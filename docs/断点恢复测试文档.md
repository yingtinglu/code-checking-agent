# 断点续跑测试指南

## 背景

对话图（`chat_agent/graph.py`）启用了 LangGraph SqliteSaver checkpointer，实现节点级状态持久化 + 断点续跑：turn 中途崩溃（进程被杀、异常）后，重启加载会话可从最后 checkpoint 续跑，不丢已完成的工具调用/中间结果。

checkpoint 在正常运行时是**隐身**的（你看不到它工作）。要验证它的价值，必须**主动制造一次 turn 中途打断**，再重启续跑。本文档给出可复现的测试方法。

## 前置条件

### 1. 测试钩子（已置于 `graph.py:execute_tools` 顶部）

一个由标记文件触发、触发即自毁的"模拟崩溃"开关：

```python
# graph.py execute_tools 顶部
import os as _os
_break_marker = _os.path.join("data", "_chkpt_break")
if _os.path.exists(_break_marker) and state.get("tool_iteration", 0) >= 1:
    try: _os.remove(_break_marker)
    except OSError: pass
    print(f"  [测试钩子] 模拟崩溃 @ execute_tools (tool_iteration={state.get('tool_iteration')})")
    raise RuntimeError("CHKPT_TEST: 模拟崩溃，用于测试断点续跑")
```

特性：

- **无标记文件则完全不触发**，生产运行零影响。
- 触发条件 `tool_iteration >= 1`：在第 2 次及以后的 execute_tools 才崩（保证崩溃前已有节点 checkpoint）。
- 触发后自毁标记文件，重启续跑时第 2 次 execute_tools 不会再崩，能跑完。

> 若不想长期保留测试钩子，测完可删除该块；保留也无害（无标记即不触发）。

### 2. 检查脚本 `inspect_checkpoint.py`（项目根）

让 checkpoint 状态可见：

- 无参：列出所有会话的 `turn_seq`/`active_thread`（标记 `[未完成]`/`[完成]`）。
- 带会话 ID：显示该会话在 sqlite 里的 checkpoint/writes 行数（崩溃前各节点状态）。

## 测试流程

### 步骤 1：确认 checkpoint 在写（正常路径）

```bash
cd D:/code/AgentDemo
python main.py
```

正常对话一轮（任意消息跑完）→ 退出。检查：

```bash
.venv/Scripts/python.exe inspect_checkpoint.py
```

预期：

- `data/checkpoints.sqlite` 存在。
- 该会话 `[完成]`、`active_thread=∅`（完成后清空，不误触发续跑）、`turn_seq=1`。

说明 checkpoint 机制已接入。

### 步骤 2：模拟崩溃 + 续跑（核心）

**① 放崩溃标记 + 起会话**：

```bash
cd D:/code/AgentDemo
.venv/Scripts/python.exe -c "import os; os.makedirs('data',exist_ok=True); open('data/_chkpt_break','w').close()"
python main.py
```

**② 输入会触发 ≥2 轮工具调用的消息**（必须 ≥2 轮 execute_tools，否则 hook 不触发）：

```
请分析 D:\code\<某已授权仓库> 的代码质量
```

→ agent 调 list_files → grep → read_file（第 2 次 execute_tools 时）触发崩溃：

```
[测试钩子] 模拟崩溃 @ execute_tools (tool_iteration=1)
错误: CHKPT_TEST: 模拟崩溃，用于测试断点续跑
[续跑] 检测到本轮未完成（turn 1，已保留断点）
是否续跑? (y/n):
```

**崩溃后 REPL 不再像正常那样直接等输入**——main.py 捕获异常后立即检测 `active_thread` 非空，就地提示续跑（第一道保险）。输 `y` → 从断点续跑完成；输 `n` → 丢弃中断的 turn，回到正常 REPL。

**③ 确认崩溃前 checkpoint 已持久化**（若上一步选了 n，先重新放标记再崩一次到这步）：

```bash
.venv/Scripts/python.exe inspect_checkpoint.py
.venv/Scripts/python.exe inspect_checkpoint.py <会话ID前8位>
```

预期：

- 该会话 `[未完成]`、`active_thread=<id>#1`（非空）。
- writes 表有 execute_tools 之前各节点（append_user_msg/load_memory/build_context/call_llm/execute_tools 第1轮）的记录。

**④ 重启续跑（模拟进程被杀，第一道保险没机会触发）**：
崩溃后**直接关终端 / taskkill 杀进程**（不输 y/n），让 `active_thread` 留存。然后：

```bash
cd D:/code/AgentDemo
python main.py
load            # 选刚才崩溃的会话
```

预期自动提示：

```
[续跑] 检测到未完成的任务（turn 1，停在节点 ['build_context']），是否续跑? (y/n):
```

输 `y` → 从断点续跑完成，agent 给出最终回答。

输 `n` 则丢弃；事后可输 `resume` 命令重新续跑。

### 步骤 3：验证续跑正确性

续跑日志开头应为：

```
[续跑] 从节点 [...] 续跑 turn <id>#1
```

且续跑**只打印崩溃后那几个节点的工具调用**——崩溃前第 1 轮 list_files/grep 的 `[工具调用]` **不应再出现**（其结果从 checkpoint 重放进 context_manager，不重新调）。

续跑完成后：

```bash
.venv/Scripts/python.exe inspect_checkpoint.py
```

该会话应变 `[完成]`、`active_thread=∅`、`turn_seq=1`。

**对比验证（可选）**：不放标记正常跑一遍，对比最终回答——应基本一致（崩溃节点的只读工具重跑结果不变）。

## 关键判据：是"续跑"还是"从头重跑"

| 续跑日志现象                                                 | 结论                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| 开头 `从节点 [...] 续跑`，只跑崩溃后节点，第 1 轮工具不再调用 | ✅ 真正断点续跑生效                                           |
| 又把第 1 轮 list_files/grep 全部 `[工具调用]` 打印一遍       | ❌ checkpoint 没用上，从头重跑，需排查 thread_id/invoke(None) |

## 续跑触发逻辑（何时提示、谁来提示、"n" 的语义）

崩溃后 `active_thread` 非空 = 有未完成 turn。系统有三道触发点确保它被处理、不被新轮无声覆盖遗弃：

| 场景                                 | 触发点                                              | y                        | n                                                            |
| ------------------------------------ | --------------------------------------------------- | ------------------------ | ------------------------------------------------------------ |
| 进程内异常崩溃（chat() 抛错）        | `main.py` chat() 的 except 块                       | 立即续跑                 | **推迟**（保留 active_thread + checkpoint，可稍后 resume / 下次 load 续跑） |
| 进程被杀 / 重启后 load 会话          | `agent.py` `_detect_and_offer_resume()`（__init__） | 续跑                     | **推迟**（同上，保留可续跑）                                 |
| 用户主动输新消息（有未完成 turn 在） | `agent.py` `chat()` 入口                            | 续跑（本次新消息不处理） | **丢弃并处理新消息**（单 active_thread 无法同时保留两个未完成 turn，开新轮必须放弃旧断点） |

手动触发：REPL 输 `resume` 命令随时续跑当前会话的未完成 turn。

**"n" 语义按场景区分**：

- 崩溃/load 提示选 n = **推迟**（非破坏性，保留可续跑）——符合"下次 load 还能故障恢复"。
- chat 入口选 n = **丢弃并继续**（用户主动开新轮，必须放弃旧断点）——这是单 active_thread 设计的必然。

**关键**：推迟后 active_thread 仍非空，REPL 继续提示输入。用户可：

- 输 `resume` → 续跑；
- 输新消息 → chat 入口再提示 y/n（y 续跑 / n 丢弃后处理新消息）；
- 输 `quit` → active_thread 持久化，下次 load 仍提示续跑。

## 原理速览（两件事，勿混淆）

- **消息重放**（续跑前重建 context_manager）：把 checkpoint 里**已记录的消息**（含工具结果字符串）重新 append 到 context_manager，**不重新调工具**。artifact 按 tool_call_id 确定性路径覆盖，幂等。
- **节点重执行**（崩溃节点续跑时）：崩溃发生在某节点中间（无 checkpoint），续跑从上一节点 checkpoint 开始，**该节点从头重跑**——重新执行其 tool_calls_result 里的工具。当前工具集只读（read_file/grep/list/bash/MCP 查询），重跑结果一致，安全。

## 收尾

- 测试钩子可保留（无标记即不触发，生产安全）或删除 `graph.py:execute_tools` 顶部 `# ── 临时测试钩子` 到 `# ── 测试钩子结束 ──` 块。
- `data/_chkpt_break` 标记已被 hook 自毁，无需手动删。
- `inspect_checkpoint.py` 可留作日常运维工具。

## 排查

| 现象                             | 可能原因                                                     |
| -------------------------------- | ------------------------------------------------------------ |
| 重启 load 没提示续跑             | 该会话 `active_thread` 为空（崩溃前 chat() 没保存到？或已正常完成）；或 sqlite 无该 thread checkpoint |
| 续跑报"context_manager 重建失败" | `rebuild_from_checkpoint` 异常，看日志详情；多因 checkpoint.messages 缺字段 |
| 续跑从头重跑                     | `graph.invoke(None, config)` 没正确 resume，检查 config 是否含 `thread_id` 且与崩溃时一致 |
| `[警告] SqliteSaver 初始化失败`  | langgraph-checkpoint-sqlite 未装或 data 目录无写权限         |
