## 五、最适合写进架构师简历的 8 条

### 1. 5 年及以上架构师通用版

- 基于 LangGraph 状态机实现多轮会话 Agent，引入 ReAct 反思（continue/replan）+ Plan/Replan 指令实现动态计划修订，工具迭代循环上限 20 轮
- 针对工具循环调用，设计参数哈希去重 + 独立轮次预算（15 次）+ 工具冷却（2 次/2 轮），保证分析链路可预测收敛
- 设计 L1-L4 分层上下文压缩（L1 落盘投影 / L2' 文本压缩 / L3' bounded 丢弃 / L4' 滚动摘要）+ 三归档策略，治理长对话上下文膨胀
- 基于 LangGraph checkpointer（SqliteSaver）实现节点级状态持久化与断点续跑，per-turn thread_id 隔离

### 2. AI 应用架构师版

- 参与 LLM 应用链路工程化，实现 ReAct 反思 + Plan/Replan 的 Agent 工具调用闭环与上下文容量治理
- 设计工具结果投影 reducer 体系，按工具语义保留定位信息，使检索链在压缩后不断裂
- 实现 Agent 长期记忆（fork agent 独立 LangGraph 后台异步提取 + Jaccard 去重 + 48h 硬判决 + search_memory 工具 + 平台话题检测）
- 实现输入/输出双向护栏（SQL 注入拦截、PII/凭证脱敏、canary 提示词泄露检测），保障 AI 应用安全边界

### 3. Agent / RAG / Workflow 架构师版

- 基于 LangGraph 实现 Workflow 状态机编排（append_user_msg→load_memory→build_context→call_llm→execute_tools→reflect→save_response→push_queue）
- 设计 ReAct 反思节点（continue/replan）+ Plan/Replan 指令注入，工具治理含参数哈希去重、轮次预算、工具冷却、失败缺口注入
- 实现 Tool Use 统一注册与分派（原生 + MCP，stdio/sse/streamable_http 三传输），含风险分级授权网关
- 实现工具结果归档三策略（archive/inline/archive_ref）与按需取回，平衡上下文容量与信息完整性
- 注：本项目未发现 RAG 检索增强（无向量库/embedding/rerank）证据，不适合写"RAG 链路建设"；长期记忆为文件检索式（Jaccard），非向量 RAG

### 4. 平台架构师版

- 设计统一工具注册表作为接入层，合并原生与 MCP 工具，对外暴露标准化 function-calling 接口
- 实现文件工具路径白名单（默认空、单目录）+ 分级授权网关 + 只读 bash 沙箱（cmdlet 白名单 + 危险操作硬禁 + UTF-8 编码治理）
- 实现文件化日志体系（agent_log 按 conv_id 写 data/logs/，全链路 set_conv_id 联动）
- 为退化分析实现 SQLite 快照缓存（复合主键 + TTL 24h + schema 版本控制 + 旧 JSON 迁移）+ LangGraph checkpoint

### 5. 分布式系统 / 存储架构师版

- 本项目不建议主打分布式存储架构师版本。未发现大规模分布式存储、元数据、副本、一致性协议、数据分片证据。

### 6. AI 性能优化架构师版

## 六、最适合面试展开的 8 条

### 1. ReAct 反思 + Plan/Replan

- 怎么问：你的 Agent 怎么决定继续还是修订计划？
- 考什么：ReAct 思想 + 反思与收敛的边界
- 怎么答：execute_tools 后 reflect 节点无工具 LLM 调用输出 DECISION（continue/replan），call_llm 按 decision 注入 Plan/Replan 指令；reflect 不判 done（最终回答由 call_llm 决定，避免过早收尾）
- 浅在哪：只说"加了反思"说不出为什么不做 done
- 深度边界：能讲 reflect 不入 context_manager 的原因（破 L2/L3 按 user 分轮 + push_queue turn 切分）
- 代码位置：`graph.py: reflect`/`route_after_reflect`/`REFLECT_PROMPT`/`PLAN_INSTRUCTION`/`REPLAN_INSTRUCTION`
- 保守答：不报准确率
- JD 映射：Agent / Workflow（强）；AI 性能优化（不匹配）

### 2. 检索防环机制

- 怎么问：Agent 怎么避免反复调用同一工具撑爆上下文？
- 考什么：硬约束 vs LLM 自主性
- 怎么答：双闸门——参数哈希去重（按工具分字段）+ 独立轮次预算（15 次，与全局迭代 20 解耦）；route_response 预算耗尽强制 final_answer
- 浅在哪：只说"加了去重"
- 深度边界：能讲换工具绕过怎么防（三件套+bash 都在 _BUDGET_TOOLS）
- 代码位置：`graph.py: _search_arg_hash`/`_BUDGET_TOOLS`/`route_response`
- 保守答：不报"重复率0%"
- JD 映射：Agent（强）

### 3. 四层上下文压缩

- 怎么问：长对话上下文怎么管？
- 考什么：分层治理 + 容量-完整性 trade-off
- 怎么答：L1 落盘投影、L2' 压 user+最终回答文本（不动工具结果）、L3' bounded 丢弃保近 3 轮、L4' 滚动摘要双输出（叙事+关键事实）；_total_tokens 统一口径
- 浅在哪：只说"会压缩"
- 深度边界：能讲 L2' 为什么不动工具结果（L1 已保真投影）
- 代码位置：`context.py: ContextManager`/`_l2_truncate_dialogs`/`_l3_drop_ancient`/`_l4_full_summary`/`_rolling_summary`
- 保守答：不报压缩比
- JD 映射：AI 应用 / Agent（强）

### 4. 断点续跑

- 怎么问：长任务崩溃了怎么办？
- 考什么：checkpoint/restart 设计
- 怎么答：SqliteSaver checkpointer + per-turn thread_id + Conversation.active_thread；resume_turn 用 rebuild_from_checkpoint（全量历史+重放本轮幂等）重建 context_manager，graph.invoke(None) 续跑；续跑/推迟/丢弃三态
- 浅在哪：只说"有 checkpoint"
- 深度边界：能讲 rebuild_from_checkpoint 为什么 compress=False
- 代码位置：`agent.py: resume_turn`/`_detect_and_offer_resume`；`context.py: rebuild_from_checkpoint`
- 保守答：不写"零故障/分布式高可用"
- JD 映射：稳定性 / Workflow（强）

### 5. 长期记忆系统

- 怎么问：Agent 怎么跨会话记忆？
- 考什么：agent memory + 异步治理 + 去重
- 怎么答：后台 fork agent 独立 LangGraph 异步提取，Jaccard 预筛返回候选让 LLM 判 create/update，48h 硬判决 + search_memory 工具主 Agent 主动检索，平台话题 PLATFORM_SKIP 跳过
- 浅在哪：只说"有记忆"
- 深度边界：能讲 Jaccard vs embedding 的取舍、两类 vs 四类
- 代码位置：`memory/fork_graph.py`/`manager.py`/`store.py`；`graph.py: load_memory`/`push_queue`
- 保守答：不写"向量/准确率"
- JD 映射：AI 应用 / Agent（强）

### 6. 路径白名单与授权网关

- 怎么问：文件工具怎么防越权？
- 考什么：纵深防御
- 怎么答：白名单默认空+受保护目录+过宽拦截+commonpath 防遍历+分级授权（high/medium）
- 浅在哪：只说"校验路径"
- 深度边界：能讲相对路径基准不一致的修复
- 代码位置：`filesystem.py: validate_path`/`confirmation.py: ConfirmationGateway`
- 保守答：不写"多租户"
- JD 映射：平台 / 安全

### 7. 只读 bash 沙箱 + UTF-8 编码治理

- 怎么问：bash 工具怎么防破坏性命令？中文输出崩了怎么办？
- 考什么：命令级安全 + 编码治理
- 怎么答：cmdlet 白名单+危险硬禁+重定向检测+cwd 约束；_PRELUDE 设 OutputEncoding=UTF8 + subprocess encoding=utf-8/errors=replace
- 浅在哪：只说"限制命令"
- 深度边界：能讲重定向正则如何避免误伤 `>500`、cancel scope
- 代码位置：`filesystem.py: _validate_bash_command`/`bash`
- 保守答：不写"容器沙箱"
- JD 映射：安全 / 平台

### 8. 输入输出护栏 + canary

- 怎么问：怎么防注入和泄露？
- 考什么：AI 应用安全边界
- 怎么答：输入 SQL 拦截+PII 检测，输出 PII/凭证脱敏+canary 泄露截断
- 浅在哪：只说"做了校验"
- 深度边界：能讲 canary 注入与检测时机
- 代码位置：`guardrails.py`/`graph.py: save_response`
- 保守答：不写"WAF"
- JD 映射：AI 应用 / 安全

### S1：ReAct 反思 + Plan/Replan

#### 1. 这个亮点一句话说人话

这个机制让 AI 助手在每调完一次工具后，先"想一下"：是继续按原计划走，还是计划需要改一改。它不靠死板的固定流程，而是让 AI 自己判断要不要调整路线，但又用硬限制兜底防止它乱跑。

#### 2. 业务背景，小白版

- 给谁用：需要多步工具调用的 AI 分析助手。
- 想完成什么：让 Agent 能动态调整分析计划，而不是死磕固定步骤。
- 出问题后果：死板循环导致方向错了也改不回来，或纯自主循环不收敛。
- 为什么不是普通 CRUD：是"用 LLM 反思驱动动态规划"的系统问题。
- 位置：`graph.py: reflect`/`route_after_reflect`。
- 适合架构师：体现 ReAct + trade-off。

#### 3. 核心术语解释

| 术语            | 小白解释                   | 代码体现                                |
| --------------- | -------------------------- | --------------------------------------- |
| ReAct           | Reason+Act，先想再做的循环 | `reflect` 节点                          |
| reflect         | 调完工具后的"反思"步骤     | `reflect` 函数                          |
| continue/replan | 继续原计划/修订计划        | `reflect_decision`                      |
| Plan/Replan     | 首次出计划/重出计划        | `PLAN_INSTRUCTION`/`REPLAN_INSTRUCTION` |

#### 4. 代码入口

```
ChatAgent.chat() [agent.py]
  -> LangGraph: call_llm -> execute_tools -> reflect [graph.py]
     -> reflect: 无工具 LLM 调用输出 DECISION: continue|replan
     -> route_after_reflect: replan→build_context(注入 REPLAN_INSTRUCTION)
                             continue→_route_after_execute
  -> 下一轮 call_llm: 按 reflect_decision 注入 Plan/Replan/continue 指令
```

#### 5. 核心代码文件清单

| 文件路径              | 类/方法                                                  | 作用       | 阅读顺序 |
| --------------------- | -------------------------------------------------------- | ---------- | -------- |
| `chat_agent/graph.py` | `reflect`                                                | 反思节点   | 1        |
| `chat_agent/graph.py` | `route_after_reflect`                                    | 反思后路由 | 2        |
| `chat_agent/graph.py` | `REFLECT_PROMPT`/`PLAN_INSTRUCTION`/`REPLAN_INSTRUCTION` | 指令       | 3        |
| `prompts/reflect.txt` | 反思提示词                                               | 引导反思   | 4        |

#### 6. 主链路逐步解释

1. LLM 调工具 → `execute_tools` 执行
2. `execute_tools` → `reflect`：无工具 LLM 调用，输出 DECISION + 理由
3. `route_after_reflect`：replan→build_context；continue→_route_after_execute
4. 下一轮 `call_llm`：按 `reflect_decision` 注入 REPLAN/PLAN/continue 指令
5. 收敛后 `call_llm` 不再调工具 → `save_response`

#### 7. 数据是怎么流动的

- 输入：当前 api_messages（含计划+工具结果）
- 中间：reflect LLM 输出 DECISION 文本
- 写入：`reflect_decision`/`reflect_reasoning` 存 state（不入 context_manager）
- 返回：route_after_reflect 决定下一节点

#### 8. 为什么这样设计

- 为什么 reflect 不判 done：避免过早收尾导致答案简短，最终回答时机由 call_llm 决定。
- 为什么 reflect 不入 context_manager：入存储会破 L2/L3 按 user 分轮 + push_queue turn 切分；作 assistant-无-tool_calls 会使下个 call_llm 以 assistant 结尾→LLM 停调工具。
- 不用会怎样：死板循环或不可控自主。
- 牺牲了什么：反思多一次 LLM 调用开销。

#### 9. Trade-off

- 自主性 vs 可控性（reflect 只判 continue/replan，硬约束守底线）
- 反思开销 vs 收敛保证
- 动态修订 vs 计划一致性

#### 10. 异常场景和兜底

- reflect LLM 调用失败：默认 continue（`full_text='DECISION: continue\n（反思调用失败，默认继续）'`）。
- 预算耗尽：route_response 在 call_llm→execute 闸口挡到 final_answer，reflect 的 continue 不生效。
- 未实现：reflect 不判 done（无 done 分支）。

#### 11. 为什么值得写架构师简历

- 体现 ReAct + 动态规划 + trade-off。
- 适合 AI 应用/Agent；不适合 AI 性能优化/分布式存储。

### S2：Agent 长期记忆系统

#### 1. 这个亮点一句话说人话

这个机制让 AI 拥有跨会话记忆：每轮对话结束后，一个后台"小助手"（fork agent，自己也是一套独立流程）异步地从对话里提取值得长期记住的信息，存成文件；下一轮对话时，主 AI 可以主动用 search_memory 工具搜出跟当前问题相关的记忆。如果是平台级话题（不是具体项目），它会自动跳过不存。

#### 2. 业务背景，小白版

- 给谁用：需要个性化、跨会话记忆的 AI 助手。
- 想完成什么：让 Agent 记住用户反馈/项目洞察。
- 出问题后果：每次对话像第一次。
- 为什么不是普通 CRUD：后台异步+独立流程+相似度去重+主动检索。
- 位置：`memory/fork_graph.py`+`manager.py`+`store.py`，接入 `graph.py: load_memory`/`push_queue`。
- 适合架构师：agent memory+异步治理。

#### 3. 核心术语解释

| 术语           | 小白解释                            | 代码体现                    |
| -------------- | ----------------------------------- | --------------------------- |
| 长期记忆       | 跨会话保存的信息                    | `.agent_memory/` 文件       |
| fork agent     | 后台独立的小 AI 流程                | `fork_graph.py`             |
| Jaccard 相似度 | 两段文本词集的交集/并集             | `jaccard_similarity`        |
| 48h 硬判决     | 只看最近48小时记忆，不靠 LLM 判时间 | `get_recent_memory_entries` |
| 平台话题检测   | 平台级话题跳过不存                  | `PLATFORM_SKIP`             |

#### 4. 代码入口

```
主流程:
  graph: append_user_msg -> load_memory(注入指令让 LLM 调 search_memory) [graph.py]
  graph: save_response -> push_queue(深拷贝本轮片段入队) [graph.py]
后台:
  MemoryManager daemon -> fork_graph.invoke() [manager.py]
    -> fork_build_context(系统提示词+已有记忆索引+本轮片段, PLATFORM_SKIP 指令)
    -> fork_call_llm(独立 LLMClient, _FORK_TOOLS)
    -> fork_route(平台话题/无工具→finish, 否则 execute_tools)
    -> fork_execute_tools(fork_read_file/fork_write_memory, Jaccard 预筛+LLM 判 create/update)
    -> fork_finish
  store.* (.agent_memory/ 文件读写; jaccard; 48h; search_memory)
```

#### 5. 核心代码文件清单

| 文件路径               | 类/方法                              | 作用            | 阅读顺序 |
| ---------------------- | ------------------------------------ | --------------- | -------- |
| `memory/fork_graph.py` | `build_fork_graph`                   | fork agent 流程 | 1        |
| `memory/manager.py`    | `MemoryManager`                      | 后台调度        | 2        |
| `memory/store.py`      | `jaccard_similarity`/`search_memory` | 存储+去重       | 3        |
| `graph.py`             | `load_memory`/`push_queue`           | 主流程接入      | 4        |
| `tools/filesystem.py`  | `_search_memory_handler`             | 主 Agent 工具   | 5        |

#### 6. 主链路逐步解释

1. 用户输入 → append_user_msg → load_memory（注入"调 search_memory"指令）
2. LLM 调 search_memory 工具 → store.search_memory（48h+Jaccard top5）返回相关记忆
3. 正常 build_context→call_llm→...→save_response
4. save_response → push_queue：深拷贝本轮片段入队
5. daemon 线程取出 → fork_graph.invoke：fork agent 提取记忆，Jaccard 预筛+LLM 判 create/update，写 .agent_memory/

#### 7. 数据是怎么流动的

- 输入：本轮 api_messages 片段 + project_root + 模型参数
- 中间：fork agent → JSON 记忆项 → Jaccard 预筛 → LLM 判 create/update
- 写入：`.agent_memory/<category>/<title>.md` + `memory_index.md`
- 检索：search_memory（48h 硬判决+Jaccard 排序 top5）

#### 8. 为什么这样设计

- 为什么异步 fork agent：不阻塞主流程。
- 为什么独立 LangGraph：fork agent 有自己的工具循环（fork_read_file/fork_write_memory，max=5）。
- 为什么 Jaccard 预筛+LLM 判：简单预筛+LLM 语义判断，无需 embedding。
- 为什么 48h 硬判决：不依赖 LLM 判时间，程序硬过滤。
- 为什么平台话题检测：平台级话题（如"平台/分发中台"）不属项目记忆，PLATFORM_SKIP 跳过。
- 牺牲了什么：Jaccard 精度低于 embedding；两类记忆（user_feedback/model_insight）非四类。

#### 9. Trade-off

- 异步不阻塞 vs 记忆延迟生效
- Jaccard 简单 vs 语义精度（未用 embedding）
- 两类 vs 四类记忆
- 平台话题跳过 vs 可能漏存

#### 10. 异常场景和兜底

- fork agent LLM 失败：重试3次，跳过快照。
- 队列满：丢弃当前快照。
- 平台话题：PLATFORM_SKIP 跳过。
- Jaccard 有相似：返回候选让 LLM 判 create/update（skipped++，等下轮决策）。
- 未实现：autoDream/矛盾检测/时序淘汰/MemoryPolicy 门卫/四类记忆/向量检索。

#### 11. 为什么值得写架构师简历

- agent memory + 独立 LangGraph fork + Jaccard + 48h + 平台话题检测，体现"后台异步+主流程主动检索"双链路。
- 适合 AI 应用/Agent；不适合 RAG（非向量）/AI 性能优化。

### S3：四层上下文压缩（L2'/L3'/L4'）

#### 1. 一句话说人话

这个机制像四道闸门治理 AI 长对话越聊越长的问题：第一道把超大工具结果存硬盘只留摘要；第二道把历史对话的"问题+最终回答"文字压缩但不动工具结果；第三道丢掉最老的对话但至少保近 3 轮；第四道让 AI 把整段历史浓缩成"叙事+关键事实"双摘要。

#### 2. 业务背景，小白版

- 给谁用：长对话/深度分析的 AI 应用。
- 想完成什么：窗口内支持多轮深度对话。
- 出问题后果：上下文超限中断。
- 为什么不是普通 CRUD：分层治理+冷热分层+按需取回。
- 位置：`context.py: ContextManager`。
- 适合架构师：容量-完整性 trade-off。

#### 3. 核心术语解释

| 术语         | 小白解释                   | 代码体现               |
| ------------ | -------------------------- | ---------------------- |
| 上下文窗口   | 模型一次能看到的最大文本量 | `max_context_tokens`   |
| 投影         | 大结果压缩成摘要           | reducer                |
| bounded 丢弃 | 丢老的但保近 K 轮          | `_L3_MIN_KEEP_TURNS=3` |
| 滚动摘要     | 按块 oldest→newest 累积    | `_rolling_summary`     |

#### 4. 代码入口

```
build_context [graph.py]
  -> ContextManager.compress_if_needed(hint) [context.py]
     -> L1(已在 append_tool_result 时做)
     -> L2: _l2_truncate_dialogs(压 user+最终回答, 不动工具结果)
     -> L3: _l3_drop_ancient(bounded 保近3轮)
     -> L4: _l4_full_summary -> _rolling_summary(滚动双输出)
  -> get_api_messages
工具结果落盘:
  execute_tools -> append_tool_result
     -> (archive) ToolArtifactStore.write [storage.py]
```

#### 5. 核心代码文件清单

| 文件路径     | 类/方法                                                      | 作用    | 阅读顺序 |
| ------------ | ------------------------------------------------------------ | ------- | -------- |
| `context.py` | `ContextManager`                                             | 总管家  | 1        |
| `context.py` | `_l2_truncate_dialogs`/`_l3_drop_ancient`/`_l4_full_summary` | 三层    | 2        |
| `context.py` | `_rolling_summary`/`_chunk_messages_by_turn`                 | L4 滚动 | 3        |
| `storage.py` | `ToolArtifactStore`                                          | 落盘    | 4        |

#### 6. 主链路逐步解释

1. 工具结果进上下文时判 L1（>4000 token 落盘投影）
2. 每轮 build_context 检查是否超 70% → L2' 压历史文本
3. 仍超 85% → L3' bounded 丢最旧（保近3轮）
4. 仍超 92% → L4' 滚动摘要双输出
5. 仍超 → _hard_truncate 硬裁剪兜底

#### 7. 数据流动

- 输入：工具结果原文 + 历史消息
- 中间：>4000 落盘；历史文本→摘要；滚动分块→双输出
- 写入：artifact 文件、`_api_messages`
- 返回：api_messages 给 LLM

#### 8. 为什么这样设计

- 为什么 L2' 不动工具结果：L1 已保真投影，工具结果是定位依据。
- 为什么 L3' bounded 保 K 轮：避免无限丢导致近期信息丢失。
- 为什么 L4' 滚动双输出：远古压缩、近期保真，叙事+关键事实分离。
- 为什么 _total_tokens 统一口径：消除"L2 后比压缩后小"的口径错觉。
- 牺牲了什么：投影丢细节（可 read_artifact 取回）；L4 摘要成本。

#### 9. Trade-off

- 上下文容量 vs 信息完整性
- L4 摘要成本 vs 容量
- bounded 保留 vs 丢弃效率

#### 10. 异常场景和兜底

- L4 LLM 摘要失败：`_rolling_summary` 返回 None → 回退 L3。
- 压缩后仍超：`_hard_truncate` 硬裁剪。
- 孤儿 artifact：启动清理。

#### 11. 为什么值得写

- 分层治理+冷热分层+按需取回+统一口径。
- 适合 AI 应用/Agent；不适合分布式存储。

#### 12. 简历表述

##### 克制专业版

设计 L1-L4 分层上下文压缩（L1 落盘投影/L2' 文本压缩/L3' bounded 丢弃/L4' 滚动摘要双输出）+ 三归档策略。

##### AI 应用架构师版

参与上下文容量治理，实现分层压缩与归档三策略。
（分布式/存储/AI 性能优化版本不适用）

#### 13. 面试三层追问

- 第一层：做了什么？四层压缩+三归档。
- 第二层：L2' 为什么不动工具结果？L1 已保真。
- 第三层：L4' 滚动双输出？L3' bounded？答"叙事+关键事实 oldest→newest 累积"；"保近3轮不无限丢"。

#### 14. 面试官验证问题

- 三归档策略对应工具。
- L4 摘要失败怎么兜底。
- _total_tokens 为什么统一口径。

#### 15. 第三层薄弱环节

- 说不清 L2' 不动工具结果原因
- 说不清 L4' 滚动双输出
- 说不清 bounded 保 K 轮

#### 16. 新人阅读路线

1. `context.py: ContextManager.__init__` → 阈值
2. `append_tool_result` → L1
3. `_compress_in_place` → L2-L4
4. `_l2_truncate_dialogs`/`_l3_drop_ancient`/`_l4_full_summary` → 三层

6. `storage.py: ToolArtifactStore` → 落盘

#### 17. 风险边界

- 不能说：分布式存储、KV Cache、压缩率95%
- 可以说：分层压缩、L2'/L3'/L4'、归档三策略、按需取回
- 需补证据：压缩比实测

### S4：断点续跑

#### 1. 一句话说人话

这个机制让长任务（要调很多轮工具的分析）在崩溃或中断后能从上次断掉的地方继续，而不是从头重来。它把每一步的执行状态存到 SQLite，下次启动检测到有没完成的任务，就重建现场接着跑。

#### 2. 业务背景，小白版

- 给谁用：多轮工具调用的长任务分析。
- 想完成什么：崩溃/中断后可恢复。
- 出问题后果：长任务从头重来浪费且不可恢复。
- 为什么不是普通 CRUD：checkpoint/restart 流程设计。
- 位置：`agent.py: resume_turn`+`graph.py: build_chat_graph(checkpointer)`+`context.py: rebuild_from_checkpoint`。
- 适合架构师：长任务可靠性。

#### 3. 核心术语解释

| 术语          | 小白解释             | 代码体现                     |
| ------------- | -------------------- | ---------------------------- |
| checkpoint    | 执行状态快照         | SqliteSaver                  |
| thread_id     | 一轮任务的标识       | `{conv_id}#{turn_seq}`       |
| active_thread | 进行中的任务         | `Conversation.active_thread` |
| rebuild       | 重建上下文到断点时刻 | `rebuild_from_checkpoint`    |

#### 4. 代码入口

```
main.py: SqliteSaver 初始化 -> ChatAgent(checkpointer)
ChatAgent.chat():
  -> turn_seq++, thread_id={conv_id}#{turn_seq}, active_thread=thread_id
  -> graph.invoke(initial_state, config={thread_id})
  -> 完成: active_thread=""
崩溃/中断: active_thread 保留
重启/load:
  -> _detect_and_offer_resume: get_state 检测 snap.next
  -> resume_turn: rebuild_from_checkpoint(全量历史+本轮消息) -> graph.invoke(None, config) 续跑
  -> 或 _discard_incomplete_turn(永久丢) / _defer_incomplete_turn(推迟)
```

#### 5. 核心代码文件清单

| 文件路径     | 类/方法                                             | 作用       | 阅读顺序 |
| ------------ | --------------------------------------------------- | ---------- | -------- |
| `agent.py`   | `resume_turn`/`_detect_and_offer_resume`            | 续跑入口   | 1        |
| `agent.py`   | `_discard_incomplete_turn`/`_defer_incomplete_turn` | 三态       | 2        |
| `context.py` | `rebuild_from_checkpoint`                           | 重建上下文 | 3        |
| `graph.py`   | `build_chat_graph(checkpointer)`                    | 编译图     | 4        |
| `storage.py` | `Conversation.turn_seq`/`active_thread`             | 状态字段   | 5        |

#### 6. 主链路逐步解释

1. chat()：turn_seq++，thread_id，active_thread=thread_id，invoke
2. 完成：active_thread=""
3. 崩溃：active_thread 保留 + checkpoint 存
4. 重启/load：_detect_and_offer_resume 查 snap.next
5. resume_turn：rebuild_from_checkpoint → invoke(None) 续跑

#### 7. 数据流动

- 输入：storage_history + turn_storage_messages
- 中间：rebuild_from_checkpoint（load_from_history compress=False + 重放本轮幂等）
- 写入：SQLite checkpoint
- 返回：续跑结果

#### 8. 为什么这样设计

- 为什么 per-turn thread_id：避免跨轮消息累积（add_messages）。
- 为什么 rebuild compress=False：_cur_turn_start=0 时压缩空转白跑 L4，留给 build_context。
- 为什么三态：续跑/推迟/丢弃匹配不同用户决策。
- 不用会怎样：崩溃从头重来。
- 牺牲了什么：单 active_thread 无法同时保留两个未完成 turn。

#### 9. Trade-off

- 持久化开销 vs 可恢复性
- 单 active_thread vs 多未完成 turn
- compress=False vs 压缩时机

#### 10. 异常场景和兜底

- 无 checkpointer：resume_turn 返回提示。
- checkpoint 已到 END：清理 active_thread。
- rebuild 失败：打印错误返回。
- 用户开新轮选 n：_discard 永久丢。

#### 11. 为什么值得写

- 长任务可靠性 + 三态决策。
- 适合稳定性/Workflow；不适合分布式高可用。

#### 12. 简历表述
