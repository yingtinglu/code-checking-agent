# 断点恢复实现细节

> 对话跑到一半崩溃后，重启能从上次断点接着跑，不丢已调的工具结果。
> 基于 LangGraph SqliteSaver checkpointer + per-turn thread_id + context_manager 重放重建。

---

## 一、整体架构

```
SqliteSaver (data/checkpoints.sqlite)
    │  节点级持久化整个 ChatAgentState，按 thread_id 索引
    ↓
Conversation (data/conversations/<id>.json)
    │  turn_seq + active_thread 标记进行中的轮次
    ↓
context_manager (内存 _api_messages)
    │  不被 checkpointer 存，崩溃丢失 → 续跑前重放重建
```

三个层次各司其职：sqlite 存 graph state、JSON 存会话元数据+完整消息、内存存工作上下文。

---

## 二、存什么

SqliteSaver 在每个节点（super-step）执行完后，自动序列化整个 `ChatAgentState`（`graph.py:83`）存入 sqlite：

| 字段                                                         | 内容                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| `messages`                                                   | 本轮已累积的 LangChain 消息（user / assistant[含 tool_calls] / ToolMessage）——重建 context_manager 的原料 |
| `tool_iteration` / `search_iteration`                        | 工具迭代次数、检索轮次预算消耗                               |
| `tool_calls_result`                                          | LLM 上次输出的工具调用（若崩溃在 execute_tools 前）          |
| `response_text`                                              | LLM 已输出的文本                                             |
| `search_called_tools`                                        | 去重表（arg_hash → tool_call_id），防续跑重复调              |
| `tool_failure_*` / `cooldown_tools`                          | 工具失败记录、冷却状态                                       |
| `reflect_decision` / `reflect_reasoning`                     | 上轮反思结论                                                 |
| `user_input` / `canary` / `conversation_id` / `model` / `temperature` / `max_tokens` | 运行参数                                                     |

**不存的**：`context_manager._api_messages`（内存活状态，进程重启即丢）。这是续跑前必须重建的对象。

按 `thread_id`（`会话ID#轮次号`）索引。每节点存一次，崩溃只丢"崩在那个节点里没跑完的部分"，之前节点的 state 都在。

---

## 三、per-turn thread_id

`messages` 字段用 `add_messages` reducer，同 thread 会跨轮累积——破坏"messages=本轮"语义。故每轮独立 thread（`agent.py:chat()`）：

```python
self.conversation.turn_seq += 1
thread_id = f"{self.conversation.id}#{self.conversation.turn_seq}"
self.conversation.active_thread = thread_id    # 标记进行中
self.storage.save_conversation(self.conversation)
result = self.graph.invoke(initial_state, config={"configurable": {..., "thread_id": thread_id}})
self.conversation.active_thread = ""            # 成功后清空
```

`turn_seq` 和 `active_thread` 存在 `Conversation`（`storage.py`），`from_dict` 用 `.get(field, default)` 向后兼容旧会话文件。

---

## 四、崩溃检测（三道保险）

崩溃后 `active_thread` 非空 = 有未完成 turn。三道触发点确保它被处理、不被新轮覆盖遗弃：

### 保险一：进程内异常（main.py except）

`main.py` 的 `chat()` try/except 捕获异常后，检测 `active_thread` 非空立即提示续跑，阻断用户直接输新消息覆盖：

```python
except Exception as e:
    print(f"\n错误: {e}")
    if agent.conversation.active_thread:
        print("[续跑] 检测到本轮未完成，已保留断点")
        confirm = input("是否续跑? (y/n): ")
        if confirm in ("y", "yes"):
            agent.resume_turn()
        else:
            agent._defer_incomplete_turn(...)   # 推迟，保留可续
```

### 保险二：进程被杀后重启 load（agent.py `_detect_and_offer_resume`）

`__init__` 加载会话后调：

```python
thread_id = self.conversation.active_thread
if not thread_id: return
snap = self.graph.get_state({"configurable": {"thread_id": thread_id}})
if snap is None or not snap.next:   # snap.next 非空 = 还有节点没跑
    self.conversation.active_thread = ""; return   # 已完成，清理
print(f"检测到未完成 turn（停在 {list(snap.next)}），是否续跑? (y/n)")
```

### 保险三：chat 入口兜底（agent.py `chat()` 开头）

```python
if self._checkpointer and self.conversation.active_thread:
    print("检测到上一轮未完成，保留断点")
    confirm = input("y=续跑 / n=丢弃并处理本次新消息: ")
    if confirm in ("y", "yes"):
        return self.resume_turn()
    self._discard_incomplete_turn(self.conversation.active_thread)
```

防新轮覆盖（新轮 chat() 会设新 active_thread，单 active_thread 无法同时保留两个未完成 turn）。

### "n" 的语义（按场景区分）

| 场景               | n 的含义                                                     |
| ------------------ | ------------------------------------------------------------ |
| 崩溃/load 提示选 n | **推迟**（`_defer_incomplete_turn`）：保留 active_thread + checkpoint，可稍后 resume 或下次 load 续跑 |
| chat 入口选 n      | **丢弃并继续**（`_discard_incomplete_turn`）：开新轮必须放弃旧断点 |

## 五、续跑流程（核心：`resume_turn`）

```python
# agent.py:resume_turn()
snap = self.graph.get_state(config)

# 5.1 重建 context_manager 到 checkpoint 时刻状态
turn_base_msgs = snap.values.get("messages", [])
turn_storage_msgs = _base_to_storage_messages(turn_base_msgs)
self.context_manager.rebuild_from_checkpoint(
    self.conversation.messages,   # 全量存储历史（turn 前）
    turn_storage_msgs,            # 本轮 checkpoint 消息
    sys_prompt,
)

# 5.2 从 checkpoint 续跑
result = self.graph.invoke(None, config)   # input=None = 从最后 checkpoint 续

# 5.3 完成清理
self.conversation.active_thread = ""
new_messages = _base_to_storage_messages(result.get("messages", []))
self.conversation.messages.extend(new_messages)
self.storage.save_conversation(self.conversation)
```

### 为什么必须 rebuild

graph 节点执行时有两种副作用：

1. 返回 state 更新 → 被 checkpointer 持久化。
2. mutate `context_manager._api_messages`（append_user/append_assistant/append_tool_result）→ **不被** checkpointer 持久化。

崩溃后 graph checkpoint 活着，但 `context_manager` 丢失。续跑前必须把 `context_manager` 重建到 checkpoint 时刻，否则续跑节点基于空/旧上下文出错。

---

## 六、rebuild 重放重建（`context.py:rebuild_from_checkpoint`）

```python
def rebuild_from_checkpoint(self, storage_history, turn_storage_messages, system_prompt):
    # 第1步：装载全量存储历史（turn 之前的完整对话），不压缩
    self.load_from_history(storage_history, system_prompt, compress=False)
    # 第2步：重放本轮 checkpoint 消息
    began = False
    for msg in turn_storage_messages:
        if not began and msg.role == "user":
            self.begin_turn()              # 标记本轮起点
            began = True
        self._append_storage_message(msg)  # 逐条重放
```

### 两个数据源

- **`storage_history`** = `conversation.messages`：存盘的完整历史（turn 开始前状态），从 JSON 会话文件读。
- **`turn_storage_msgs`** = checkpoint 里 `snap.values["messages"]` 转成 storage 格式：本轮已累积的消息（user → assistant[计划+tool_calls] → tool 结果 → ...）。

### 重放幂等性（为什么安全）

`_append_storage_message` 按消息类型处理：

- **user/assistant 文本**：直接 append 到 `_api_messages`，无副作用。
- **tool 结果**：调 `append_tool_result`，其中 L1 落盘按 `tool_call_id` 确定性命名（`storage.py:_safe_artifact_id`），同 id 覆盖同文件——重放覆盖，不产生重复 artifact。

### 为什么 `compress=False`

`load_from_history` 默认装载完会压缩。但此刻 `_cur_turn_start=0`（还没 begin_turn），压缩会把全部消息当"当前轮"保护 → L3 一轮不丢、L4 白跑 LLM 摘要却压不下。故 rebuild 传 `compress=False` 跳过，等续跑的 build_context 在 `_cur_turn_start` 正确后再压。

---

## 七、两类"重放"的区别（勿混淆）

|              | 消息重放（rebuild）                                          | 节点重执行（续跑）                  |
| ------------ | ------------------------------------------------------------ | ----------------------------------- |
| 做什么       | 把 checkpoint 里**已记录的消息**重新 append 到 context_manager | 崩溃节点从头重跑其 tool_calls       |
| 重新调工具吗 | **不调**，工具结果从 ToolMessage.content 取                  | **调**（崩溃节点无部分 checkpoint） |
| 范围         | 本轮到 checkpoint 的所有消息                                 | 仅崩溃那一轮节点的 tool_calls       |
| 安全性       | 幂等（artifact 按 tool_call_id 覆盖）                        | 工具只读，重跑结果一致              |

## 八、checkpoint 粒度

节点级（LangGraph 默认，每节点完成后存）。崩溃在节点中间 → 该节点无 checkpoint，回退到上一节点 checkpoint 重跑整节点。execute_tools 中间崩 → 重跑整个 execute_tools（同 tool_calls_result，工具只读，安全）。

要做"工具级 checkpoint"（execute_tools 第 2 个工具崩了只重跑第 2 个）需把 execute_tools 拆子图或用 LangGraph Send API，本期未做——只读工具重跑安全，节点级够用。

---

## 九、流程图

```
正常 turn:
  chat() → turn_seq+1, active_thread=thread_id, save → invoke → 成功 → active_thread="" → save

崩溃（节点中间）:
  chat() → ... → 崩在某节点 → active_thread 留存（未清）

重启 load 会话:
  __init__ → _detect_and_offer_resume:
    active_thread 非空 → get_state → snap.next 非空 → 提示续跑
      y → resume_turn():
           rebuild_from_checkpoint(history, turn_msgs, sys)  # 重放重建 _api_messages
           graph.invoke(None, config)                        # 从 checkpoint 续跑
           active_thread="" + 追加 messages + save
      n → _defer_incomplete_turn (保留可续) / chat 入口 _discard (丢弃)

手动续跑:
  REPL 输 resume → agent.resume_turn() → 同上
```

## 十、边界与限制

- **非只读工具**：当前工具集（文件读/grep/list/bash 只读/MCP 平台查询只读）均幂等，节点重跑安全。未来加写操作工具需在其内部做幂等或 finer-grained checkpoint。
- **checkpoint 体积**：节点级全 state 序列化，含 messages（BaseMessage）。大 turn checkpoint 较大但 sqlite 可承受；如成瓶颈可只存 diff（LangGraph 支持，后续优化）。
- **并发**：同会话不并发跑（REPL 单线程），无需锁；多进程同时跑同会话不在支持范围。
- **孤儿 checkpoint**：`_discard_incomplete_turn` 只清 active_thread，sqlite 里的 checkpoint 留为孤儿（不删，占点空间但不误触发续跑）。彻底清理需调 checkpointer 删该 thread（LangGraph 删除 API 是异步的，本期未做）。
- **turn_seq 持久化**：每次 chat() 增 turn_seq 要 save_conversation（已有 save 流程，加字段即可）。
